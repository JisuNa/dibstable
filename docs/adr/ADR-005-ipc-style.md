# ADR-005: 프로세스 간 통신 — REST + Kafka, 아웃박스로 원자화

- **상태**: 승인
- **날짜**: 2026-08-02
- **관련 장**: 3장 (프로세스 간 통신)

## 문제

[ADR-004](ADR-004-service-boundaries.md)에서 서비스를 셋으로 나눴다. 이제 이들이 **무엇으로 어떻게 대화할지** 정해야 한다. 모놀리스에서 공짜였던 메서드 호출이 여기서는 네트워크를 건너고, 그 선택이 가용성을 좌우한다.

## 강제 조항

- [system-operations.md §6](../architecture/system-operations.md)에서 계산했듯 **동기 호출 체인의 가용성은 곱으로 떨어진다** (3서비스 ≈ 98.5%).
- 예약 생성은 세 서비스에 걸친 데이터 변경이라 원자성이 필요한데, 2PC는 쓸 수 없다(4장 사가).
- DB 변경과 메시지 발행이 어긋나면 시스템이 불안정해진다 (3.3.7).
- 순서가 뒤바뀌면 안 되는 이벤트가 있다(같은 식당의 변경분).
- 브로커는 **적어도 한 번** 전달하므로 중복이 온다.
- 1인 학습 프로젝트 — 운영 컴포넌트를 늘릴수록 부담이 커진다.

## 해법

**동기는 REST, 서비스 간 통신은 Kafka 비동기 메시징을 주로 쓴다.** 세부 결정은 다음과 같다.

| 결정 | 선택 | 근거 |
|---|---|---|
| 동기 프로토콜 | **REST** (성숙도 레벨 2) | 단순·익숙, curl로 검증 가능. gRPC는 이 프로젝트에 이점이 없다 |
| 비동기 브로커 | **Kafka** | 샤딩된 채널로 **순서 보장 + 수평 확장**을 동시에 얻는다 (3.3.5). 책 예제와도 정합 |
| DB 변경 + 메시지 발행 | **트랜잭셔널 아웃박스** | 로컬 ACID 트랜잭션만으로 원자성 확보, 2PC 불필요 (3.3.7) |
| 아웃박스 릴레이 | **폴링 발행기** | 규모가 작으면 폴링으로 충분하다는 저자 권고. 로그 테일링(Debezium)은 폴링 비용이 문제될 때 |
| 메시지 ID | **아웃박스에 저장된 UUID** (`message_id` 컬럼) | 아래 상세 |
| 발행분 처리 | **DELETE** (워터마크 금지) | 아래 상세 |
| 순서 보장 | 애그리거트 ID를 **파티션 키**로 | 같은 식당의 이벤트는 같은 파티션 → 한 컨슈머가 순서대로 처리 |
| 중복 처리 | **`processed_messages` 테이블** | 메시지 ID를 비즈니스 변경과 **같은 트랜잭션**으로 기록, 중복이면 무시 (3.3.6) |
| 메시지 포맷 | **JSON** | 사람이 읽을 수 있고 스키마 변경에 관대. 이진 포맷의 효율이 필요한 규모가 아니다 |
| 인프라 주소 | 구성 파일 + 환경 변수 | 서비스 디스커버리는 서비스 간 동기 호출이 생기는 시점(8장 게이트웨이)에 재검토 |

컬럼 매핑은 [service-apis.md](../architecture/service-apis.md)가 단일 출처다. 여기서는 **왜 그렇게 정했는지**만 남긴다.

#### 메시지 ID를 UUID로, 발행 시점에 만들지 않는 이유

두 가지를 동시에 막아야 한다.

1. **릴레이가 발행할 때마다 새로 만들면 안 된다.** 크래시 후 재발행 시 ID가 달라져 컨슈머가 중복을 걸러내지 못한다.
2. **AUTO_INCREMENT PK를 그대로 쓰면 안 된다.** 서비스마다 1, 2, 3…이 독립적으로 매겨져, 여러 서비스가 발행하기 시작하는 4장부터 **컨슈머가 남의 메시지를 중복으로 오인해 조용히 버린다.**

그래서 아웃박스에 `id BIGINT AUTO_INCREMENT`(폴링 순서용)와 `message_id CHAR(36)`(전역 유일 UUID)를 **따로** 둔다. 헤더로 나가는 것은 `message_id`이고, INSERT 시점에 확정된 뒤 바뀌지 않는다.

#### 워터마크 방식을 금지하는 이유

`WHERE id > 마지막_발행_ID`로 폴링하면 **이벤트가 영구히 유실된다.** AUTO_INCREMENT는 채번 순서와 커밋 순서가 다르기 때문이다 — 트랜잭션 A가 id=5를 채번한 채 아직 커밋 전인데 B가 id=6을 먼저 커밋하면, 릴레이는 6을 읽고 워터마크를 6으로 올린다. 뒤늦게 커밋된 5는 다시는 조회되지 않는다(6.1.4).

따라서 **발행에 성공한 행은 DELETE**한다. 아웃박스는 영구 저장소가 아니라 임시 메시지 큐다(3.3.7).

#### 순서 보장의 전제 — 릴레이 인스턴스 1개

파티션 키만으로는 부족하다. **릴레이가 여러 개면 같은 행을 중복 발행하고 순서도 깨진다.** 3장은 단일 인스턴스를 전제하며, 12장에서 서비스를 X축 복제할 때 `SELECT ... FOR UPDATE SKIP LOCKED`나 리더 선출(ShedLock 등)로 이 전제를 지켜야 한다.

### 서비스 내부 구조 — 육각형 아키텍처

[ADR-004](ADR-004-service-boundaries.md)가 3장으로 미뤄 둔 패키지 규약을 여기서 확정한다.

```
com.dibstable.<service>
├── domain/                      비즈니스 로직 — 엔터티, 포트(인터페이스)
├── adapter/
│   ├── inbound/web/             REST 컨트롤러
│   ├── inbound/messaging/       이벤트 컨슈머
│   ├── outbound/persistence/    JPA 리포지터리 구현
│   └── outbound/messaging/      아웃박스·이벤트 발행
└── config/
```

**비즈니스 로직은 어댑터에 의존하지 않는다** — 반대로 어댑터가 비즈니스 로직에 의존한다 (2.1.2). 디렉터리는 실제 클래스가 생길 때 만들고, 빈 디렉터리를 미리 두지 않는다.

> `in`/`out`이 아니라 `inbound`/`outbound`인 이유: **`in`은 Kotlin 하드 키워드**라 `package ...adapter.in.web`이 컴파일되지 않는다. 백틱으로 감쌀 수는 있으나 모든 import에 전염된다.

## 결과 맥락

- **장점**
  - 브로커가 버퍼링하므로 컨슈머가 죽어 있어도 발행 측은 계속 동작한다 → 가용성이 곱으로 깎이지 않는다.
  - 아웃박스로 "저장은 됐는데 메시지가 안 나갔다"는 상태가 구조적으로 불가능해진다.
  - 파티션 키·멱등 처리로 순서와 중복을 동시에 해결한다.
- **단점**
  - 운영 컴포넌트가 둘(MySQL·Kafka) 늘어난다.
  - 폴링 발행기는 지연(폴링 주기)과 DB 부하를 감수한다.
  - 최소 한 번 발행이므로 **모든 컨슈머가 멱등해야 한다** — 하나라도 빠뜨리면 중복 처리 버그가 난다.
- **새로 생긴 이슈**

| 이슈 | 해결 | 장 |
|---|---|---|
| 동기 외부 호출(토스 PG)의 부분 실패 — 타임아웃·미처리 요청 제한·회로 차단기 | Resilience4j를 PG 어댑터에 적용 | **4장** |
| 세 서비스에 걸친 예약 생성의 원자성 | 사가 | 4장 |
| 폴링 지연이 문제가 되면 | 트랜잭션 로그 테일링(Debezium) | 필요 시 |
| API 하위 호환 깨는 변경이 생기면 — 경로 버저닝(`/v1`) | 외부 API 노출 시점에 결정 | 8장 |
| 계약 위반을 자동으로 잡기 | 컨슈머 주도 계약 테스트 | 9장 |
| 릴레이를 여러 인스턴스로 띄우면 중복 발행·순서 붕괴 | `FOR UPDATE SKIP LOCKED` 또는 리더 선출 | 12장 |
| 서비스 간 동기 호출이 생기면 주소를 어떻게 찾나 | 서비스 디스커버리 (배포 플랫폼 내장) | 8·12장 |

> **회로 차단기를 3장에서 적용하지 않는 이유**: 3장 시점에는 방어할 동기 외부 호출이 없다. 유일한 자연스러운 대상은 토스 PG인데 결제는 4장에 등장한다. 억지 호출을 만들어 붙이느니 4장의 실제 호출에 적용한다. 참고로 **사가 자체는 메시지 기반이라 동기 호출을 만들지 않는다** — PG 호출이 유일한 대상이다.
