# ADR-002: 리포지토리 전략 — 모노레포 + Gradle 멀티모듈

- **상태**: 승인
- **날짜**: 2026-07-19
- **관련 장**: 1장 (프로세스), 2장 (분해 전략 — 모듈 경계)

## 문제

6개 서비스로 성장할 MSA 코드베이스를 하나의 리포에 둘 것인가, 서비스별 리포로 나눌 것인가.

## 강제 조항

- 실무 MSA는 팀 자율성을 위해 폴리레포(서비스별 리포)가 일반적이다.
- 이 프로젝트는 1인이 장 단위로 **여러 서비스를 가로지르는 리팩터링**을 반복한다 (예: 3장 아웃박스 도입, 11장 관측성 일괄 적용).
- 서비스 독립성(ADR-001 수용 기준)은 리포 구조와 무관하게 지켜져야 한다.

## 해법

**모노레포 + Gradle 멀티모듈**을 채택한다.

- 서비스 = Gradle 서브프로젝트. 공통 빌드 설정은 **루트 `build.gradle.kts`의 `subprojects {}` 블록**으로 중앙화.
- 버전은 `gradle/libs.versions.toml`(version catalog) 단일 소스로 관리.
- **모듈 의존성 규칙**: 서비스 모듈 간 코드 의존 금지. 통신은 런타임 API·이벤트 계약으로만. 공유 모듈은 안정 유틸만 (2장에서 규칙 상세화).

> **변경 이력 (2026-07-19)**: 최초 결정은 `build-logic/` convention plugin 방식이었으나, 현 규모에서는 루트 방식의 단순함이 낫다고 판단해 전환. 모듈 타입이 분화되어(WebFlux 게이트웨이·비Boot 라이브러리 등) `subprojects {}` 안에 조건 분기가 쌓이기 시작하면 convention plugin으로 재전환한다.

## 결과 맥락

- **장점**: 장 단위 원자적 커밋(여러 서비스 변경을 하나의 PR로), 단일 빌드·단일 버전 카탈로그, 빌드 구조가 파일 하나로 즉시 파악됨, 학습 이력이 한 리포에 남음.
- **단점**: "독립 배포"가 리포 수준에서 강제되지 않아 규율에 의존 — 서비스 간 코드 참조가 기술적으로 가능해짐. `subprojects {}`는 전 모듈 일괄 적용이라 모듈 타입이 갈리면 분기가 필요함(위 재전환 조건).
- **새로 생긴 이슈**: 모듈 의존성 규칙을 어떻게 강제하나 → 2장에서 Gradle 설정(또는 ArchUnit)으로 검증 도입 검토. 모듈 타입 분화 시점 감시 → 8장(게이트웨이) 착수 시 재평가.

## 연관 패턴

- **대안 — 폴리레포 (기각)**: 팀별 소유·독립 배포에 유리하나 1인 학습에서는 리포 6개 관리 오버헤드만 남는다.
- **후행자**: 2장 서비스 모듈 구성, 12장 서비스별 컨테이너 빌드.
