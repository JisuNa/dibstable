# ADR-004: 서비스 경계 — 예약·식당·결제 3분할

- **상태**: 승인
- **날짜**: 2026-08-02
- **관련 장**: 2장 (분해 전략)

## 문제

[ADR-001](ADR-001-microservice-architecture.md)에서 MSA를 채택했다. 이제 경계를 실제로 어디에 그을 것인가 — 특히 **다툼의 여지가 있는 지점들**을 결정해야 한다.

각 시스템 작업이 어느 서비스에 배정되는지는 [system-operations.md](../architecture/system-operations.md)의 표가 유일한 출처다. 이 문서는 그 배정에 이르기까지 **논쟁이 된 4가지 결정**만 기록한다.

## 강제 조항

- 비즈니스 능력별 분해와 하위 도메인별 분해는 대안 관계지만, 이 도메인에서는 **같은 경계**를 산출한다 (책 2.2.3).
- **SRP**(하나의 변경 사유)와 **CCP**(함께 변경되는 것을 같은 서비스로)가 서로를 견제한다 — 잘게 쪼개면 SRP는 만족하지만 CCP가 깨져 분산 모놀리스가 된다.
- 분해할수록 네트워크 왕복이 늘고 동기 체인의 가용성이 곱으로 떨어진다 (2.2.5).
- FTGO와 대응 관계를 유지하면 책 예제를 그대로 이식할 수 있다 — 다만 도메인이 다르면 억지로 맞출 이유는 없다.
- 1인 학습 프로젝트로 서비스 상한은 6개.

## 해법

**reservation · restaurant · payment 3개 서비스**로 시작한다(7장 search, 8장 gateway, 13장 waiting 추가). 다음 4가지가 그 결정의 실질이다.

### ① 식당 정보와 타임슬롯 재고를 한 서비스로 묶는다

FTGO는 음식점 서비스와 주방 서비스를 나눈다. DibsTable은 나누지 않는다.

**근거**
- **CCP**: 영업시간·휴무일·정원 정책은 같은 사유로 함께 바뀐다. 사장님이 한 화면에서 관리한다.
- 슬롯 조회는 거의 항상 식당 정보를 동반한다 — 분리하면 네트워크 왕복만 늘어난다 (2.2.5 네트워크 지연).
- **정원 불변 값이 `TimeSlot` 애그리거트 안에서 완결된다.** 분리해서 얻는 것이 없다.

**FTGO와 다른 이유**: FTGO의 음식점/주방은 **액터가 다르고**(본사 정보 관리 vs 주방 직원) **생애주기가 다르다**(반영구적 메뉴 vs 주문 건별 티켓). DibsTable의 식당/슬롯은 액터도 생애주기도 같다.

**반론(기록해 둔다)**: 재고는 예약 오픈 순간 쓰기가 폭주하고 식당 정보는 읽기 위주다 — 확장 특성이 다르다. 지금은 X축 복제로 충분하다고 판단했다.

**재분리 조건** — 아래 중 하나라도 관측되면 재검토한다:
- 슬롯 쓰기 부하 때문에 식당 정보 조회의 응답 시간이 흔들린다
- 식당 정보와 슬롯이 서로 다른 사유로 각각 변경되는 일이 반복된다
- 두 기능의 배포 주기가 갈린다

### ② 고객·사장님 신원을 소유하는 서비스를 만들지 않는다

FTGO에는 소비자 서비스가 있지만, DibsTable 6서비스에는 없다.

**결정**: `customerId`·`ownerId`는 요청과 함께 **외부에서 주어지는 불투명 값**으로 취급한다. 프로필 관리는 [범위 제외](../requirements.md)이며, 실제 발급·검증은 11장 JWT가 담당한다.

**근거**: 고객 프로필 CRUD는 이 프로젝트가 가르치려는 어떤 패턴도 실습시키지 않는다. 유령 서비스를 만들지 않는다.

**결과 — 신뢰 경계**: 서비스는 `customerId`의 실재 여부를 검증하지 않고, 게이트웨이가 인증했다고 신뢰한다. 11장 이전까지는 **인증되지 않은 값을 그대로 받는 상태**임을 명시해 둔다.

### ③ 갓 클래스 `Reservation`을 서비스별 관점 모델로 해체한다

모놀리스였다면 `Reservation` 하나가 고객 정보·식당 정보·시간·인원·결제·환불·상태를 전부 들고 있었을 것이다. 책 2.2.5의 `Order` 갓 클래스와 같은 상황이다.

| 서비스 | 클래스 | 갖는 것 | **모르는 것** |
|---|---|---|---|
| reservation | `Reservation` | 상태 기계, `customerId`·`restaurantId`·`timeSlotId`(PK 참조), 인원, 예약금액 | 고객 이름·연락처, PG 거래 상세, 슬롯 정원 |
| restaurant | `TimeSlot` | 날짜, 시간, 정원, 선점 수 | **누가 예약했는지** |
| payment | `Payment` | `reservationId`(PK 참조), 금액, PG 거래 ID, 승인·환불 이력 | 예약이 무엇인지, 식당이 무엇인지 |

**핵심**: 세 서비스가 같은 "예약"을 각자의 관점으로 본다. 애그리거트 간 참조는 객체 레퍼런스가 아니라 **PK 값**이므로 서비스 경계를 넘는 참조가 존재하지 않는다.

흩어진 정보를 화면 하나로 합치는 일은 8장 API 조합의 몫이고, 세 서비스에 걸친 일관성은 4장 사가의 몫이다.

### ④ 모듈 의존 규칙은 규율로 강제한다 — [ADR-002](ADR-002-monorepo-gradle-multimodule.md) 미결 종결

ADR-002가 "2장에서 Gradle 설정 또는 ArchUnit으로 검증 도입을 검토"한다며 열어 둔 항목을 닫는다.

**결정**: 서비스 모듈 간 Gradle 의존을 **선언하지 않는다**는 규율로 간다. 자동 검증 장치는 도입하지 않는다.

**근거**: 모듈 간 의존이 0인 상태에서 강제 장치부터 만드는 것은 YAGNI다. 위반이 발생할 표면 자체가 아직 없다.

**도입 조건**: 공유 모듈이 실제로 생기거나, 위반이 한 번이라도 발생하면 그때 ArchUnit을 넣는다.

## CCP 점검 — 반례 시나리오

"이 요구사항이 바뀌면 몇 개 서비스를 고쳐야 하나?" 2개 이상이면 경계를 의심한다 (2장 실무 체크리스트).

| 변경 시나리오 | 고칠 서비스 | 판정 |
|---|---|---|
| 취소 기한 1일 → 3일 | reservation | ✅ 1개 |
| 예약금 정액 → 인원당 과금 | reservation | ✅ 1개 |
| 슬롯 정원 → 좌석 단위 배치 | restaurant | ✅ 1개 |
| PG사 교체 (토스 → 타사) | payment | ✅ 1개 |
| 예약 상태 추가 (방문 완료) | reservation | ✅ 1개 |
| **노쇼 시 예약금 몰수** | reservation(판정) + payment(몰수) | ⚠️ **2개** |

마지막 항목이 걸린다. 다만 "예약 판정"과 "돈 처리"는 본질적으로 다른 능력이라 **경계를 옮겨서 해결될 문제가 아니고**, 두 서비스 협동을 사가로 푸는 것이 정답이다. 이런 유형이 반복해서 늘어나면 그때는 경계를 재검토한다.

## 결과 맥락

- **장점**
  - 세 서비스 모두 단일 책임을 가지며, CCP 점검을 실질적으로 통과한다(경계선 1건은 사가로 해소).
  - 갓 클래스 해체로 서비스 경계를 넘는 객체 참조가 없다 → 5장 애그리거트 규칙과 그대로 맞물린다.
  - 외부 PG 의존이 payment 한 곳에 갇혀 결함이 격리된다.
- **단점**
  - 식당+재고 병합은 두 기능의 확장 특성 차이를 의도적으로 무시한 선택이다.
  - `customerId`를 검증하지 않는 신뢰 경계가 11장까지 열려 있다.
  - 예약 생성이 3서비스 협동이라 동기 구현 시 가용성이 98.5%로 떨어진다.
- **새로 생긴 이슈** — 후속 장이 해결한다

| 이슈 | 해결 | 장 |
|---|---|---|
| 3서비스 동기 협동의 가용성 하락 | 비동기 메시징 | 3장 |
| 3서비스에 걸친 예약 생성의 원자성 | 사가·보상 트랜잭션 | 4장 |
| 정원 검사와 차감 사이의 경합 | 애그리거트 불변 값·낙관적 잠금 | 5장 |
| 흩어진 예약 정보를 화면 하나로 | API 조합 / CQRS | 7·8장 |
| `customerId` 발급·검증 | JWT | 11장 |

## 연관 패턴

- **선행자**: [ADR-001](ADR-001-microservice-architecture.md) 마이크로서비스 아키텍처
- **대안**: 하위 도메인별 분해 — 이 도메인에서는 비즈니스 능력별 분해와 **같은 경계**를 산출해 실질적 선택지가 아니었다.
- **후행자**: 3장 IPC, 4장 사가, 5장 애그리거트, 7장 CQRS, 8장 API 게이트웨이

> **서비스 내부 구조(육각형 아키텍처)의 패키지 규약은 3장으로 미룬다.** 이름 붙일 어댑터가 아직 0개라, 첫 인바운드·아웃바운드 어댑터가 생길 때 실물과 함께 정하는 편이 낫다.
